## 2. Shared pre-admission helper

`libs/execution/readiness_evidence.record_pre_admission_evidence(...)` (used by `execute_from_packet`, `execute_order`,
and `ApprovalService.prepare_readiness_evidence`) captures the existing authoritative values (intent_id, runtime
instance, generation, recovery_required, portfolio/open-order reconciliation, readiness verdict/reasons/computed-at,
guard enabled/verdict/reason, broker_submission_allowed, execution mode, symbol/side/quantity, run/order
correlation) and persists them before admission. Required order:

readiness/guard decision -> R6 evidence -> admission / Step5C -> `execute_owned_order` -> broker submit.

## 3. Final mutation choke point

`execute_owned_order(..., readiness_evidence=None)`: for real-mode new BUY/SELL (api kt10000/kt10001/ORDER_SUBMIT,
or BUY/SELL action) it checks the reference against durable storage: exactly one hash-valid `pre_broker_submit`
record for the same intent_id/side/symbol/quantity, `guard_verdict=ALLOW`, `broker_submission_allowed=true`, age
<= 600 s. Missing -> `readiness_evidence_required`; invalid/ambiguous -> `readiness_evidence_invalid`. Both return
`NOT_SENT` before any physical/intent claim and with no broker call. No new authority: readiness/guard decisions
remain with their owners.

Operator impact: real-mode BUY/SELL approvals via `approval_cli` need a runtime `readiness_state` (or a valid
reference); without it they are blocked before admission. Mock mode and CANCEL/MODIFY are unchanged.

## 4. Atomic append and replay contract

- Critical section under a per-day interprocess lock (`<day>.jsonl.lock`, `O_CREAT|O_EXCL`, bounded wait 5 s,
  stale-lock breaking at 30 s -- same pattern as `libs/kiwoom/token_refresh_guard.py`): read valid records ->
  dedup -> allocate `intent_sequence` -> append -> fsync -> read-back verify. Storage serialisation only.
- Lock timeout / any I/O error = write failure = no admission, no broker call (never fail-open).
- Same intent + same attempt (same readiness computation + verdicts) -> same `record_id`; later callers get a
  deterministic duplicate result. New legitimate attempt -> new `record_id`, next `intent_sequence`.
- Only lines that parse and verify `record_hash` are evidence; a crashed writer's fragment is isolated on its own
  line and ignored; success requires read-back verification. `EXECUTION_READINESS_EVIDENCE_ROOT` overrides the
  storage location (operator configuration, never taken from a reference).
